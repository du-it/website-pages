In leistungsstarken Backend-Diensten müssen regelmäßig Datenbestände im Arbeitsspeicher bereinigt werden – etwa beim Entfernen deaktivierter Benutzerkonten aus einer Batch-Verarbeitungsliste. Ziel dieser Aufgabe ist es, alle inaktiven Konten (AccountStatus.DISABLED) aus einer bestehenden Liste zu filtern, ohne unnötig neuen Speicher auf dem Heap zu allozieren.

Problemstellung

Typische Standardlösungen erzeugen beim Filtern eine zweite Liste für die verbleibenden Elemente. Bei Millionen von Datensätzen erzeugt dies jedoch spürbaren Speicher-Overhead und erfordert zusätzliche Arbeit für den Garbage Collector.

Wie lässt sich die Bereinigung als In-Place-Operation umsetzen, um den Zusatzspeicher von O(N) auf O(1) zu reduzieren? Welcher Performance-Gewinn ergibt sich daraus im direkten Benchmark?

Bisheriger Ansatz (Stream API)

Der klassische Weg in modernem Java nutzt die Stream API, filtert alle aktiven Einträge heraus und sammelt diese in einer neu instanziierten Liste: 

public static void main(String[] args) {
    List<UserAccount> accounts = new ArrayList<>();
    Random random = new Random();
    IntStream.rangeClosed(1, 10_000_000).forEach(i -> {
        AccountStatus status = random.nextBoolean() ? AccountStatus.DISABLED : AccountStatus.ACTIVE;
        accounts.add(new UserAccount(status));
    });

    System.out.println("Klassischer Stream-Ansatz:");
    measurePerformance("Stream-Filter", () -> cleanupDisabledAccounts(accounts));
}

private static List<UserAccount> cleanupDisabledAccounts(List<UserAccount> accounts) {
    return accounts.stream().filter(
            acc -> acc.status == AccountStatus.ACTIVE
    ).toList();
}

Der Knackpunkt liegt in der Methode cleanupDisabledAccounts(): 

private static List<UserAccount> cleanupDisabledAccounts(List<UserAccount> accounts) {
    return accounts.stream().filter(
            acc -> acc.status == AccountStatus.ACTIVE
    ).toList();
}

Bei Aufruf von .toList() wird eine völlig neue Liste auf dem Heap erzeugt. Der Speicheraufwand wächst dadurch proportional zur Elementanzahl (O(N)). Ein In-Place-Algorithmus schaltet diesen Speicher-Overhead aus, indem er die Daten direkt im bestehenden Array neu anordnet (O(1)).

Zeitkomplexität: O(N), da jedes Element der Liste genau einmal überprüft werden muss.

Speicherkomplexität: O(N), da für die gefilterten Objekte ein neues Listenkonstrukt angelegt wird.

Hintergrund: Speicherkomplexität O(N) vs. O(1)

Die Landau-Notation (O-Notation) beschreibt, wie stark der Ressourcenbedarf skaliert, wenn die Eingabemenge N ansteigt:

  • O(N) – Linearer Speicheraufwand: Für jeden Datensatz benötigst du anteilig zusätzlichen Speicherplatz.
    Beispiel: Verdoppelt sich die Datenmenge von 50 auf 100 Millionen Konten, verdoppelt sich auch der benötigte Arbeitsspeicher für die Ergebnisliste.
  • O(1) – Konstanter Speicheraufwand: Der verbrauchte Zusatzspeicher bleibt konstant niedrig – unabhängig davon, ob die Liste 10 oder 100 Millionen Elemente enthält.
    Beispiel: Es werden lediglich zwei primitive Index-Variablen (Zeiger) im Stack vorgehalten, um Elemente innerhalb der Original-Liste zu verschieben.

Die In-Place-Lösung (Zwei-Zeiger-Muster)

Statt Elemente mit list.remove() einzeln zu löschen (was bei einer ArrayList wegen des ständigen Nachrückens der Folgeelemente zu teurem O(N²)-Laufzeitverhalten führt), nutzen wir das Lese-Schreib-Zeiger-Muster (Two-Pointer Pattern).

Funktionsweise des Algorithmus:

Wir durchlaufen die Liste in einem einzigen Durchgang und überschreiben inaktive Einträge direkt durch nachfolgende aktive Elemente:

  • Schreibzeiger (writeIndex): Startet bei Index 0 und markiert die nächste Zielposition für ein gültiges (aktives) Konto.
  • Lesezeiger (readIndex): Durchwandert die Liste fortlaufend von Anfang bis Ende und prüft den Status jedes Eintrags.

Sobald readIndex auf ein aktives Konto stößt, wird dieses an die Position von writeIndex kopiert und writeIndex um 1 erhöht. Inaktive Konten werden vom Lesezeiger schlicht übergangen.

Abschließend erzeugt accounts.subList(0, writeIndex); eine View auf den aktiven Teilbereich – ohne Erzeugung einer neuen Liste im Speicher. 

public static List<UserAccount> cleanupDisabledAccountsInPlace(List<UserAccount> accounts) {
    int writeIndex = 0;
    for (int readIndex = 0; readIndex < accounts.size(); readIndex++) {
        UserAccount account = accounts.get(readIndex);
        if (account.isActive()) {
            accounts.set(writeIndex, account);
            writeIndex++;
        }
    }
    return accounts.subList(0, writeIndex);
}

Zeitkomplexität: O(N) – Ein einziger linearer Durchlauf durch das Array.

Speicherkomplexität: O(1) – Der Speicherbedarf beschränkt sich auf den Zähler writeIndex.

Performance- & Speichermessung

Mit der in der Applikation integrierten Messmethode ergeben sich bei 10 Millionen Test-Datensätzen folgende Ergebnisse im direkten Vergleich: 

public static void measurePerformance(String label, Runnable task) {
    System.gc();
    Runtime runtime = Runtime.getRuntime();
    long memBefore = runtime.totalMemory() - runtime.freeMemory();
    long start = System.currentTimeMillis();

    task.run();

    long duration = System.currentTimeMillis() - start;
    long memAfter = runtime.totalMemory() - runtime.freeMemory();

    System.out.println(label + ":");
    System.out.println("  Laufzeit: " + duration + " ms");
    System.out.println("  Zusatzspeicher: " + String.format("%.1f", (memAfter - memBefore) / (1024.0 * 1024.0)) + " MB");
}
